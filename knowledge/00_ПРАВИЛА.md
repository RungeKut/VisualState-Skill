# Правила работы с базой знаний VisualState-Kit

Этот файл — закон для базы. Он написан для ИИ, который проектирует
автоматы в IAR Visual State, и читается первым при любом изменении
документации.

Главная мысль: **база ценна не объёмом, а достоверностью**. Запись, которой
нельзя доверять, хуже отсутствия записи. Все правила ниже подчинены одному
— отделять проверенное от предполагаемого.

---

## 1. Назначение и границы

Хранить здесь:

* поведение Visual State (Coder, HCoder, Verificator, Validator, Designer,
  Control Center, State Machine API), расходящееся с документацией или с
  интуицией;
* командные строки, ключи, коды возврата, подобранные опытом;
* приёмы, доказавшие работоспособность на реальных моделях;
* решения, которые дались через несколько провалившихся попыток.

**Не хранить:**

* то, что есть в документации IAR и легко ищется (`<установка>\doc\
  UserGuide.chm`, `doc\StateMachineAPI\html`) — вместо копии ссылка и
  только расхождение с реальностью;
* устройство кода `vskit/` — оно в docstring рядом с кодом;
* историю конкретного проекта;
* **что бы то ни было о проектируемом изделии**: название, децимальный
  номер, имена его автоматов, состояний, событий, действий, переменных,
  назначение режимов, протоколы. Примеры — на примерах поставки
  (`examples\CDPlayer`, `examples\AVSystem`) или на отвлечённых моделях
  («кнопка», «лампа»);
* пути, имена серверов и учётные записи машины;
* общие сведения о Python, C и автоматах как таковых.

Проверка на нужность: *«если этого не записать, сколько времени потеряет
следующая сессия?»* Меньше десяти минут — не записывать.

## 2. Структура

```
knowledge/
  00_ПРАВИЛА.md      этот файл
  INDEX.md           плоский индекс: id, файл, когда читать
  10_API/            как вызывать: формат модели, Coder, Verificator,
                     Control Center, State Machine API
  20_ПРИЁМЫ/         как работать: подходы, доказавшие себя
  30_ГРАБЛИ/         что ломается и почему; каждая запись — потерянный час
  40_СРЕДА/          установка, версии, лицензия, репозиторий
```

Файлы нумеруются внутри раздела: `30-04_имя.md`. Номер не
переиспользуется. **Один файл — одна тема**, предел — около 200 строк.

---

## 3. Обязательная шапка

```yaml
---
id: 30-04
title: Короткая формулировка факта, а не название темы
tags: [coder, ошибка, триггер]
applies_to: Visual State 9.1.1.3863
status: проверено | не проверено | устарело
verified: 2026-10-12 — как именно проверено
source: СПОСОБ получения знания: эксперимент, документация
---
```

| status | Что означает | Как использовать |
|---|---|---|
| `проверено` | Воспроизведено на реальном Visual State, с датой и способом | Можно опираться без перепроверки |
| `не проверено` | Из документации, по аналогии | Перепроверить перед применением; результат записать |
| `устарело` | Было верно, перестало быть | Не применять; хранится ради истории |

**Записи без `verified` не имеют силы.** `applies_to` **обязано называть
версию**. Внутри записи `проверено` всё непроверенное помечается словами
«не проверено» прямо в тексте.

`title` — **утверждение, а не тема**. Плохо: «Про Verificator». Хорошо:
«Verificator с неизвестной системой выходит с кодом 0».

## 4. Как ПОЛЬЗОВАТЬСЯ базой

От дешёвого к дорогому:

1. `skill/SKILL.md` — уже в контексте.
2. `knowledge/INDEX.md` — одна таблица, читается целиком.
3. Конкретный файл базы — читается целиком.
4. Код `vskit/` — docstring актуальнее пересказа.
5. Документация IAR: `doc\UserGuide.chm` (для поиска — `hh.exe
   -decompile <папка> UserGuide.chm`, затем поиск по .htm),
   `doc\StateMachineAPI\html\index.html`; справка по ключам —
   `vk.options_help("hcoder")`.
6. Эксперимент — на копии модели. Результат обязательно записывается.

**Опыт важнее документации.** Расхождение — верить базе и перепроверять
только при смене версии.

---

## 5. Как ДОБАВЛЯТЬ записи

1. Убедиться, что записи нет (`INDEX.md`, поиск). **Дубликат хуже
   пробела.**
2. Выбрать раздел, взять следующий свободный номер.
3. Написать файл по шаблону раздела 6.
4. **Обезличить** отдельным шагом: перечитать и убрать всё, по чему
   узнаётся изделие, включая имена состояний и событий его модели.
5. Строка в `INDEX.md`, строка в `CHANGELOG.md`.
6. Перед коммитом — `python tools/check_docs.py --project "<папка
   проекта>"` и `git diff` глазами ([40-02](40_СРЕДА/40-02_работа_с_репозиторием.md)).

Знание о коде дублируется одной-двумя фразами в docstring функции
`vskit/` со ссылкой на запись.

## 6. Шаблон записи

```markdown
---
id: 30-09
title: Утверждение одной строкой
tags: [...]
applies_to: Visual State 9.1.1.3863
status: проверено
verified: 2026-10-12 — чем подтверждено
source: эксперимент на копии примера CDPlayer
---

# Заголовок

## Что происходит
Команда, код возврата, строка вывода.

## Почему
Причина, если известна. Неизвестна — так и написать.

## Как правильно
Рабочий код.

## Как неправильно
Вариант, который выглядит разумно и не работает.

## Чем подтверждено
Что запускали, что получили.
```

«Как неправильно» обязателен для `30_ГРАБЛИ`.

---

## 7. Как ОБНОВЛЯТЬ записи

Правка существующего файла, а не новый файл. Обновить `verified`. Если
поведение изменилось с версией — старое утверждение уходит в раздел
«История» с версией. `title` в файле и в `INDEX.md` — если сменилась суть.
Строка в `CHANGELOG.md`.

**Понижение статуса**: запись `проверено` не сработала — сразу `не
проверено` с пометкой о расхождении.

---

## 8. Как УДАЛЯТЬ записи

По умолчанию не удаляют, а помечают `устарело`. Удалять можно дубликат
(оставив ссылку) и запись, оказавшуюся неверной, — со строкой в
`CHANGELOG.md`. Номер не переиспользуется.

---

## 9. Проверка целостности

Перед каждым коммитом и после смены версии Visual State:

* каждый файл `knowledge/` есть в `INDEX.md` и наоборот, таблицы целы;
* нет двух файлов с одинаковым `id`, у `проверено` есть `verified` и
  `applies_to`;
* включён хук `commit-msg` (`core.hooksPath` = `tools/hooks`);
* для клона задан автор коммитов (без `--global`);
* **ни один файл набора** не упоминает изделие: сверка с
  `tools/stoplist.txt`, с `--project` — ещё с именем папки проекта, именами
  `.vsp/.vsr` и именами внутри моделей (состояния, события, действия);
* `tools/stoplist.txt` есть на машине и не лежит под git.

Скрипт: `python tools/check_docs.py --project "<папка проекта>"`.

---

## 10. Язык и стиль

* Русский. Термины — автомат, состояние, событие, действие, переход,
  условие (guard), регион; имена ключей, функций и элементов XML — как
  есть.
* Числа с единицами: «0.1 с», «30 с».
* Никаких «обычно», «как правило», «должно работать» в записях
  `проверено`.
* Код в примерах — рабочий целиком. В коде набора комментариев нет;
  пояснения — в docstring модулей и функций.

## 11. Версия: база собрана на Visual State 9.1.1.3863

Всё, что записано до 12.10.2026, получено на **IAR Visual State 9.1.1.3863**
(`vk.version()`), Windows 10 64-bit, Python 3.13, arm-none-eabi-gcc 10.3.1,
lxml 6.1.3. **На другой версии** запись `проверено` читается как `не
проверено`, пока не подтверждена. Самое вероятное расхождение:

* номер формата файлов (`format="11"` в .vsp/.vsr) и схема XML — Designer
  новой версии пишет новый формат, `vskit.design` пишет 11;
* ключи Coder/HCoder (`vk.options_help()`);
* поведение Control Center (перевод строки, ответы на ошибки).

Прогнать `tests\` после обновления Visual State; упала проверка — найти
запись, перепроверить, обновить по разделу 7.
