# Работа с репозиторием

Набор — git-репозиторий (`https://github.com/RungeKut/VisualState-Kit`) и
разворачивается на нескольких машинах. Всё закоммиченное должно быть
пригодно для публичного репозитория, даже если сейчас он закрыт.

## Порядок

```bash
cd "$VSKIT_HOME"
git pull --rebase                                        # В НАЧАЛЕ работы
# ... правки набора ...
git diff                                                 # прочитать глазами
python tools/check_docs.py --project "<папка проекта>"   # стоп-слова
git add -A && git commit -m "что и почему" && git push   # СРАЗУ после правки
```

Push отклонён — `git pull --rebase`, потом push снова. **После слияния —
проверку заново и перечитать слитое**: git сливает текст, а не смысл
(в соседнем наборе так испортилась таблица индекса: две строки слились в
одну; `check_docs.py` считает ячейки в строках таблиц).

## Изделие в набор не попадает

Убирается всё, по чему узнаётся изделие:

* название, децимальный номер, имена файлов и папок проекта;
* **имена из его модели**: автоматы, состояния, события, действия,
  переменные, их пояснения; назначение режимов;
* протоколы, команды, назначение выводов МК;
* пути, серверы, учётные записи;
* **снимки диаграмм и окон рабочего проекта** (Designer, Validator):
  на картинке читаются имена. Снимки живут во временной папке сессии или в
  `tests/vyvod/`, в репозиторий не кладутся (стоп-лист картинки не видит).

Остаётся: поведение Visual State, командные строки, коды, примеры на
`examples\` поставки или на отвлечённых моделях («кнопка», «лампа»).
Проверки на рабочем проекте — только через `tests/test_project.py` с
путём аргументом; вывод — в `tests/vyvod/` (в `.gitignore`).

### Стоп-лист — только локальный

`tools/stoplist.txt` в `.gitignore`, заводится `setup.ps1`, у каждой
машины свой. Новое изделие — строка туда **до** первого коммита.
`check_docs.py` считает ошибкой и отсутствие файла, и его возвращение под
git (`git rm --cached tools/stoplist.txt`).

`check_docs.py --project "<папка>"` добавляет к стоп-словам имя папки,
имена `.vsp/.vsr` в ней и подпапках и **имена внутри моделей** (системы,
автоматы, состояния, события, действия, переменные — целиком, от 5
символов, кроме служебных `initial1`, `Region1`...). Хук `commit-msg`
проверяет текст коммита по стоп-листу и `git config vskit.project`.

### Автор коммита — задан для клона

```bash
git config user.name  "<публичное имя>"
git config user.email "<публичный адрес>"
```

Без этого git возьмёт глобальные (рабочие) имя и адрес. `check_docs.py`
требует автора на уровне клона. Не задан — не коммитить, а спросить
человека.

**`gh auth login` из агентской оболочки не запускать** — висит без
терминала.

## GitHub без gh

На машине может не быть `gh`. Для публикации хватает git с сохранённым
доступом к github.com (Диспетчер учётных данных Windows) и REST API:

```bash
TOKEN=$(printf 'protocol=https\nhost=github.com\n\n' | git credential fill | sed -n 's/^password=//p')
curl -s -H "Authorization: token $TOKEN" https://api.github.com/user/repos \
     -d '{"name":"VisualState-Kit","description":"...","private":true}'
```

Новый репозиторий заводится закрытым (`"private": true`); открывает его
владелец отдельным решением. **`gh auth login` из агентской оболочки не
запускать** — интерактивная команда без терминала висит вечно. Нет доступа —
попросить человека выполнить вход в своём терминале.

## Вклад без права записи: pull request

Push в репозиторий отклонён с `403` / `Permission denied` — право записи
только у владельца. Доступ не подбирать и не обходить: изменение уходит
**pull request'ом из своего форка**:

```bash
gh repo fork RungeKut/VisualState-Kit --remote --remote-name=fork
git switch -c <тема-латиницей>
# ... правки набора; перед пушем — тот же порядок, что перед коммитом:
# git diff глазами, python tools/check_docs.py, чистый текст коммита ...
git push fork <тема-латиницей>
gh pr create --repo RungeKut/VisualState-Kit --title "что и почему" \
     --body "check_docs.py — расхождений нет; <суть изменения>"
```

Правила те же, что для коммита: обезличивание, стоп-слова (заголовок и
текст PR — тоже), записи базы по `00_ПРАВИЛА.md` (статус, строка в
`INDEX.md`, строка в `CHANGELOG.md`). Один PR — одна тема. Свой PR не
сливать: решает владелец.

Нет `gh` — то же через REST API по токену из `git credential fill`
(раздел «GitHub без gh»): форк — `POST /repos/{owner}/{repo}/forks`,
далее push в свой форк обычным git, PR —
`POST /repos/{owner}/{repo}/pulls` с `head` = `<логин>:<ветка>`. По
документации GitHub API; на машинах набора этот путь не проверен.

## Владельцу: разбор pull request'ов

Чужие правки приходят PR'ами и ждут разбора: в начале работы, вместе с
обязательным `git pull --rebase`, — проверить и принять или вернуть:

```bash
gh pr list                             # пусто — работаем дальше
gh pr diff <N>                         # прочитать целиком, глазами
gh pr checkout <N>                     # и прогнать check_docs.py
gh pr merge <N> --rebase               # история линейная
git pull --rebase                      # подтянуть слитое в клон
```

Принимается только то, что прошло бы обычный коммит: обезличивание (diff
читается глазами — стоп-лист ловит названия, а не описания узлов и не
картинки), `check_docs.py` без расхождений, записи базы по правилам.
**Особое внимание — исполняемым файлам** (`tools/setup.ps1`,
`tools/hooks/*`, `*.py`): после слияния они окажутся на машине владельца и
будут запускаться. Не прошло проверку — не сливать, а вернуть с
пояснением: `gh pr review <N> --request-changes --body "что поправить"`.
«Слить и поправить потом» нельзя: репозиторий может быть открыт, и
содержимое увидит кто угодно сразу после слияния.

Нет `gh` — список и слияние через REST API:
`GET /repos/{owner}/{repo}/pulls?state=open`, слияние —
`PUT /repos/{owner}/{repo}/pulls/{N}/merge` с `{"merge_method":"rebase"}`.
Слияние, отвечающее 403, — вы не владелец: разбор пропустить.

## Установка на новой машине

```powershell
git clone https://github.com/RungeKut/VisualState-Kit.git
cd VisualState-Kit
powershell -ExecutionPolicy Bypass -File tools\setup.ps1
```

Затем перезапустить Claude Code / Kimi Code: скиллы перечисляются при
старте.
